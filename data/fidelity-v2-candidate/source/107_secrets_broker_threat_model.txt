Threat Model: Central Secrets Broker

System Description

The secrets broker issues short-lived credentials to workloads after authenticating workload identity. It sits between applications and backend credential authorities such as databases, cloud IAM, PKI, and third-party service accounts.

The broker is intended to reduce distribution of long-lived static secrets. It does not eliminate secrets; it centralizes and shortens their lifecycle.

Assets

Primary assets:
- root or intermediate signing keys;
- backend credential authority tokens;
- secret templates and policies;
- workload identity mappings;
- issued credentials;
- audit records;
- revocation state.

Security Objectives

1. Only authorized workload identities receive credentials.
2. A credential is scoped to the minimum required resource and lifetime.
3. Compromise of one workload does not expose credentials for another.
4. Broker compromise is detectable and blast radius is constrained.
5. Sensitive material is not exposed through logs, metrics, caches, or debugging interfaces.
6. Administrative policy changes are attributable and reviewable.

Trust Boundaries

Boundary A: workload -> broker API.
Boundary B: broker -> identity verifier.
Boundary C: broker -> backend credential authority.
Boundary D: broker -> key-management/HSM service.
Boundary E: administrators -> policy plane.
Boundary F: broker -> audit pipeline.

Threat: Stolen Workload Token

An attacker who steals a workload's identity token may attempt to request credentials.

Mitigations:
- short identity-token lifetime;
- audience binding to the broker;
- issuer validation;
- nonce or proof-of-possession where platform supports it;
- source workload attributes;
- broker-issued credential lifetime shorter than or comparable to identity lifetime.

The broker must not accept a token intended for another service merely because its signature is valid.

Threat: Identity Confusion

Two namespaces or clusters could present similarly named service accounts.

Mitigation: policy keys use full identity tuple:
(cluster_id, trust_domain, namespace, service_account)

Human-readable service names are display metadata only.

Threat: Broker SSRF

If credential templates allow arbitrary backend URLs, an attacker might use the broker to access metadata services or internal endpoints.

Mitigations:
- backend connectors are configured, not caller-supplied URLs;
- egress allowlist;
- no generic HTTP fetch capability in credential templates;
- network segmentation.

Threat: Policy Escalation

An administrator with write access could grant a workload broader secrets.

Mitigations:
- policy changes through reviewed source control or strongly authenticated admin API;
- separation between policy author and production approver for high-risk roles;
- immutable audit records;
- explicit diff showing new resource scope.

Threat: Credential Leakage in Logs

A failed backend request may include secret material in error text or URLs.

Mitigations:
- structured logging with allowlisted fields;
- redaction before log serialization;
- never log response bodies from credential authorities;
- tests containing sentinel secret values that must not appear in logs.

Threat: Cache Cross-Tenant Leakage

Broker may cache generated credentials for performance.

Mitigation: cache key includes complete identity, resource, requested scope, and policy version. Prefer not caching bearer credentials when issuance cost is acceptable. Cache entries are encrypted in memory where platform capability exists and expire aggressively.

Threat: Replay of Broker Response

A captured credential may be replayed until expiry.

Mitigation depends on credential type:
- short TTL;
- network/resource restrictions;
- mTLS-bound certificates;
- database role restrictions;
- token audience;
- revocation for high-risk credentials.

Threat: Signing-Key Theft

If broker signing keys are extracted, attacker can mint credentials without broker policy.

Mitigations:
- non-exportable HSM/KMS key;
- signing API access restricted to broker workload identity;
- key usage audit;
- rotation;
- separate keys by environment and credential class.

Threat: Broker Compromise

Assume remote code execution in one broker instance.

Design limits blast radius:
- broker does not possess plaintext master secrets when backend can issue dynamically;
- HSM keys non-exportable;
- backend roles limited by environment;
- per-instance identity;
- short-lived issued credentials;
- no cross-environment administrative token in runtime.

Compromise still remains severe because the attacker may request credentials permitted to broker authority. Runtime anomaly detection and rapid key/role revocation are required.

Threat: Availability Attack

Applications may depend on the broker for startup or periodic credential renewal.

Mitigations:
- horizontally redundant broker;
- credential renewal begins well before expiry;
- bounded client caching of still-valid credentials;
- circuit breakers against a failing backend;
- independent deployment failure domains.

Clients must not cache expired credentials indefinitely during outage.

Threat: Audit Suppression

An attacker may try to issue credentials while disabling audit.

Mitigation: high-risk issuance requires successful append to durable audit queue before response. Lower-risk operations may use asynchronous audit but expose loss metrics.

Audit destination uses separate credentials not writable for deletion by broker runtime.

Abuse Cases

1. Compromised workload requests every resource allowed by an overly broad wildcard.
Control: policies avoid wildcard resources; enumerate role classes.

2. Developer copies production identity token into test environment.
Control: trust domain and environment issuer binding.

3. Operator enables debug endpoint exposing process environment.
Control: production build disables generic debug dump; secrets never passed through environment variables when avoidable.

4. Backend returns long-lived credential despite requested short TTL.
Control: broker validates returned expiry and rejects credentials exceeding policy.

5. Clock skew causes credentials with future `not_before`.
Control: NTP monitoring and bounded validity overlap.

Data Retention

Audit retains:
- requesting identity;
- policy version;
- credential type;
- resource;
- issuance timestamp;
- expiry;
- result;
- correlation ID.

Audit does not retain secret value.

Emergency Revocation

Runbook supports:
- disable one workload identity;
- disable one policy;
- revoke one backend role;
- rotate signing key;
- deny issuance by environment;
- invalidate active certificate serials where supported.

Residual Risks

Centralization creates a high-value target and dependency. The design accepts this in exchange for eliminating broad static-secret distribution. Security therefore depends on strong identity verification, non-exportable keys, narrow backend authority, auditable policy, and short credential lifetime.

Threat-model conclusion: the broker should be treated as a security control plane, not as an ordinary secret retrieval API.
